# Claude Code — tigerwolves

A mobile-first web app for **North Brooklyn Runners (NBR)**. Currently serves TigerWolves — the Tuesday morning quality workout run. The long-term vision is to expand to all NBR runs.

Live at: https://tigerwolves.foulox.me (custom domain, since the 2026-07-03 Clerk production cutover — `tigerwolves.vercel.app` still works as a fallback alias)

Demo: https://demo.tigerwolves.foulox.me — the demo is its **own** Vercel project (`tigerwolves-demo`, deploys from `main`), with its **own** Clerk instance and PostHog project, reading the durable `demo-data` Neon branch directly via its own `DATABASE_URL` (no `DEMO_DATABASE_URL` override — that was retired in #429 once the demo became first-class; #427/#429). A distinct, curated, **persistent** environment — NOT the `test-data` E2E-wipe data (see the three-database split in Tooling Notes). Share this instead of the raw Vercel URL when showing the authenticated/leader view. Dedicated login: `foulox+demo@gmail.com`, a real **demo-instance** Clerk account distinct from the CI/Playwright test-leader one, so demo browsing doesn't pollute PostHog's leader/runner usage split.

## Diagnosing & claims — evidence before assertion

**When something is broken, or you're explaining *why* something is the way it is, you may not state a cause you have not confirmed with a command run *this session*.** Show the command and its output. A plausible causal chain is not evidence — run the query, read the file, hit the endpoint. Work one hypothesis at a time and get the evidence that would *disprove* it before you act on it. "Don't tell me the cause — show me the query that proves it."

**Treat this file, the wiki, and any doc as hypotheses to verify against the live system — not ground truth** — especially for anything that changes (databases, deployments, env vars, which branch serves what data). Docs drift; #346's own acceptance criteria flagged this very file as stale. If a doc states a fact you're about to rely on, confirm it against reality first.

**Don't assume you're blocked — test.** If you believe a permission or mode prevents an action, *attempt the read-only version first* and escalate to Lou only on an *actual* denial. Cautionary tale (2026-09-18): an agent spent an entire session guessing at a live demo bug because it assumed "Auto Mode blocks the database" (from the Tooling Note below) and never once tried a query — Lou was in auto-edit the whole time; the block was imagined, and a single `SELECT` on turn one would have replaced hours of theorizing with the answer.

## Key Constraints
- Volunteer club, no budget — keep hosting and services free/cheap
- Mobile-first: late posts happen because planning requires a computer
- Non-technical users: UI must be simple enough that it can't be "broken"
- `touch-manipulation` on all interactive elements to fix mobile Safari tap issues
- `aria-label` on any icon-only button (no visible text) — a `title` tooltip alone isn't reliably read by screen readers once there's no text to fall back on. Caught by `/review` on #172 when text-label header buttons were replaced with icon-only ones.

## Guardrails (do not reintroduce these bugs)
- **Auth: write access requires `publicMetadata.role === 'leader'` — a valid session alone is not enough.** `requireAuth()` in `app/actions.ts` throws `Unauthorized` for any signed-in user without this metadata. Both Production and Development Clerk instances run in **Open mode** (anyone can sign up); the role assignment in Clerk is the only gate. **Never remove or bypass the `publicMetadata.role` check in `requireAuth()`** — it's the only thing preventing a self-signed-up account from getting write access. To grant leader access, set `publicMetadata: { role: 'leader' }` on the Clerk user. Full detail: [Architecture Overview → Auth model](https://github.com/foulox/tigerwolves/wiki/Architecture-Overview#auth-model).
- **Cache invalidation: use `updateTag('tigerwolves-data')`, not `revalidateTag`** — this Next.js version requires `revalidateTag` to take a second cache-life-profile argument; `updateTag` is the correct single-argument primitive for read-your-own-writes inside a Server Action. Getting this wrong (tagging the cache but never invalidating it) was a real bug in #85 — writes appeared to succeed but the UI showed stale data for up to 5 minutes. **`updateTag` only works inside a Server Action** — call it from a Route Handler and you get a hard runtime error naming `revalidateTag` as the replacement (with that same second-argument requirement, e.g. `revalidateTag('tigerwolves-data', 'max')`). And any write that bypasses the app's own mutation paths entirely — raw SQL from a script, a direct DB console query — invalidates nothing at all; `fetchData`'s cache keeps serving the pre-write result for up to 5 minutes regardless of what actually changed underneath it. Hit this for real building #143's e2e seed script (`scripts/seed-e2e.ts`), which writes fixture rows with raw SQL — `app/api/e2e-revalidate/route.ts` exists specifically to give that script a way to invalidate the cache it can't otherwise touch.
- **`proxy.ts` hardcodes `signInUrl: '/sign-in'`** — don't move this back to an env var. Without it, `auth.protect()` falls back to redirecting unauthenticated visits to Clerk's Account Portal, which caused a real production sign-in loop (#157, 2026-07-03).
- **Claude must never apply the `ready-to-build` label.** It signals Lou has personally reviewed and cleared a story to build — that judgment isn't Claude's to make.
- **`position: sticky`'s "stuck" range is scoped to its containing block, not visually-adjacent content.** If that block spans more area than the section you want the element to hover over, it won't un-stick where you'd expect from the visual layout alone — you have to check the actual DOM ancestor chain. Caused a real overlap bug in the Schedule page's past/upcoming scroll-position pill (#236, 2026-07-26).
- **A third-party "ArchMe" architecture-awareness tool (MCP server + `PreToolUse` hook) was tried and fully removed (2026-08-02) — don't reinstall without asking Lou first.** First found partially installed and unknowingly live: its hook fired on nearly every `Bash`/`Grep`/`Glob` call, twice specifically right after commands touching credential-adjacent content (a `.env.local` path, a `PLAYWRIGHT_TEST_EMAIL`/`PASSWORD` grep pattern), each time suggesting the agent forward the literal command/pattern to ArchMe's own `query()` MCP tool. Initially treated as a possible prompt-injection-shaped pattern and paused via `git stash` rather than assumed benign. On full review, the installer and hook source turned out to be straightforward — no network calls in the hook itself, no credential handling, fails open safely, and `query()` is ArchMe's real documented tool rather than an unregistered destination. Lou decided to remove it anyway, on its own merits (not a security incident) — the stash was dropped and all install artifacts (`.mcp.json`, `.claude/hooks/archme-search-nudge.mjs`, `.claude/skills/architecture/`) are gone.
- **Every new Server Action call site needs its own try/catch + `Sentry.captureException`, not just the first one written for a feature.** An unguarded `await` on a Server Action throws uncaught into the Server Action boundary and trips `global-error.tsx` ("Something went wrong") for the user. Building #209 (2026-08-02), this exact crash was fixed once in the original component, then reintroduced verbatim when that component was swapped for a new one during live Preview review — the fix didn't travel with the pattern, it had to be re-applied by hand at the new call site.
- **A `ResizeObserver` on `document.body` doesn't fire when a child's height changes, if `body` itself is a fixed-height box.** RootLayout sets `html`/`body` to `h-full` (height pinned to the viewport) and only `main` gets `min-h-full` (allowed to grow). So `document.body`'s own rendered box never changes size when content inside it grows — only elements without a fixed height (like `main`, or the specific element you actually care about) do. Observe the actual element, not a fixed-height ancestor you're hoping will proxy for it. Caused a real bug: the Schedule page's fixed pill had its `top` set from the header's height measured once at mount, with a `ResizeObserver(document.body)` meant to re-run that measurement once Clerk's `<UserButton />` finished hydrating and changed the header's real height — the observer never fired, so signed-in leaders got a pill positioned partly under the sticky header (#246, 2026-07-27). Fix: observe `header` directly.

## Tooling Notes
- **Vercel CLI must be v54+** for reliable non-interactive env var management — v52's `vercel env add <name> preview --value ... --yes` (no git-branch arg, meant to apply to all Preview branches) silently fails with a `git_branch_required` error even though the CLI's own suggested fix is the exact command you just ran. Use `npx vercel@latest` for env commands if the global install is older.
- Vercel's Neon integration auto-provisions an isolated DB branch per git branch (`preview/<branch-name>`) for Preview deployments — `vercel env ls` showing one `DATABASE_URL` name for both Preview and Production does NOT mean they share a value; the integration resolves it differently per deployment. Verify actual isolation via `neonctl branches list` if this matters, don't infer from `env ls` alone.
- **Neon's free tier caps at 10 branches**, and old story branches' Neon branches do NOT get cleaned up automatically — not even when the git branch itself is deleted (confirmed 2026-07-06: two Neon preview branches for already-deleted git branches were still sitting there). Hitting the cap makes a *new* branch's Preview deployment fail the build with `DATABASE_URL is not set`, which looks like a code/env bug but isn't. After a story merges, delete its Neon branch directly (`neonctl branches delete <id> --project-id <id>`) — don't assume deleting the git branch is enough. `neonctl` needs an interactive browser OAuth on first use, but non-interactive flags (`--project-id`, `--org-id`) skip the CLI's interactive picker menus once a cached credential exists (`~/.config/neonctl/credentials.json`).
- **Local `next dev`/`next build` don't work** — `DATABASE_URL`, `GITHUB_TOKEN`, and other secrets were only ever provisioned in Vercel for Preview and Production, never Development. This is a deliberate (if implicit) choice, not a bug: testing happens via Vercel Preview URLs for every PR, not local dev. `vercel env pull` won't fix this — pulling the Development environment returns almost nothing, confirming those vars simply don't exist for that target. **`npm run test:e2e` is the closest thing to an exception** (#143) — it reads its own `.env.test` (test-data `DATABASE_URL` + Clerk test creds), never `.env.local`, so once `.env.test` is fully populated it runs locally same as in CI. It needs Clerk API keys too (`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` + `CLERK_SECRET_KEY`, whichever Clerk instance the leader test account actually lives on) — without them the dev server silently falls back to a generic Clerk demo instance, and `e2e/auth.setup.ts` fails with "Couldn't find your account," which reads like a bad password but isn't. See `.env.test.example`.
- **Three-database split — production / test-data / durable demo** — these are distinct Neon branches with different durability contracts; do not confuse them (#346, topology updated #429):
  - **Production** (`br-square-river-atjn0mzq`, host `ep-super-waterfall-atysqpip`) — live data. `.env.local`'s `DATABASE_URL` points here; treat it as production at all times. **The branch-id slug (`square-river`) and the compute-endpoint host slug (`super-waterfall`) differ** — a host-safety guard keyed on the branch-id slug will falsely reject the real production connection (hit 2026-09-18 applying #402's migration, aborting a legitimate prod write). Guard on `super-waterfall`, or match the fetched `connection_uri` host against `.env.local`'s `DATABASE_URL` host (the authoritative production pointer).
  - **test-data** (Neon branch `br-tiny-darkness-at3q6q1y`, host `ep-fragrant-sunset`; renamed from `preview/staging` in #429 — the compute-endpoint host is stable across a Neon branch rename, so the seed guard value didn't change) — `scripts/seed-e2e.ts` deletes and reinserts known fixture rows on every `npm run test:e2e` run, locally and in CI. Don't put anything here that expects to survive; don't point anything at this branch that expects durable data. The script refuses to run against any other `DATABASE_URL` host as a guard against ever touching production.
  - **Durable demo** (`demo-data`, Neon branch `br-little-rice-at9l08ja`, host `ep-ancient-math-atvtz5p9`) — a copy-on-write branch from production, holds stable demo content. The demo Vercel project (`tigerwolves-demo`) reads it directly via its own manually-set `DATABASE_URL` — **no Neon integration** on that project (the integration, deploying from `main`, would resolve `DATABASE_URL` to production), and **no `DEMO_DATABASE_URL` override** (retired in #429). **Do not wipe this branch** — it is the data backing `demo.tigerwolves.foulox.me`.
- **Demo login and leader-link** — `foulox+demo@gmail.com` is a real **demo-instance** Clerk account (its own Clerk instance since #427) with a `run_leaders` row and a self-follow linking it to the TigerWolves run. **Resetting `demo-data` from production drops this link** — production doesn't know about this demo account. Re-apply by running `scripts/refresh-demo.ts` (see below).
- **Demo SCHEMA auto-syncs on merge; `refresh-demo` is for on-demand DATA resets only (#415).** Two separate sync paths, don't conflate them: (1) demo **schema** — `.github/workflows/sync-demo-schema.yml` replays the full merged migration set (`scripts/run-migrate.ts`) against `demo-data` on every push to `main`, so a merged data-model change reaches the demo with no manual step. Lightweight, idempotent, schema-only — it never re-forks or wipes data, and is host-guarded to `ep-ancient-math` (via `MIGRATE_ONLY_HOST`) so it can't touch production or the test-data branch. (2) demo **data** — `refresh-demo.ts` (below) still exists but is now only for an on-demand data reset, not schema upkeep. Before #415 the schema had no auto-sync path at all, which is how `demo-data` silently missed #404's `run_workouts` table.
- **A PR touching `scripts/migrate*.sql` is auto-flagged `data-model-change` + a merge checklist (#428) — decide the `demo-data` path BEFORE merge.** `.github/workflows/data-model-flag.yml` (on `pull_request`; `pull-requests: write` only; per-PR concurrency; no secrets/checkout — reads the changed-file list off the Pulls API, matching `^scripts/migrate[^/]*\.sql$`, i.e. base `migrate.sql` + `migrate-*.sql`, excluding the `.gs` lib) stamps the label and posts an idempotent checklist comment (find-by-`<!-- data-model-change-flag -->`-marker, edit-in-place, so re-runs never stack), and **retracts both** if a later push drops the migration — flag only, never blocks. It's the deliberate-decision half of the hybrid guardrail whose auto-apply half is `sync-demo-schema.yml` (above): **safe** (additive/idempotent) migrations auto-apply to `demo-data` on merge, nothing to do; **risky** (drop / rename / destructive backfill) ones hit demo's *divergent* durable data, where blind apply silently corrupts/loses content — so at merge choose one: let auto-apply run, apply manually with care, or full `refresh-demo.ts` re-fork. (Fork-origin PRs would 403 on the read-only token — moot for this private solo repo; if it ever opens up, move to the `pull_request_target` pattern.)
- **`scripts/run-migrate.ts` applies `migrate.sql` + every `migrate-*.sql`** in order (base first, then numeric ascending), idempotently — it's the single "bring a DB current" command. Every migration in the repo is replay-safe by design (`IF NOT EXISTS` / `DROP CONSTRAINT IF EXISTS` then `ADD` / `WHERE NOT EXISTS` / `ON CONFLICT` / constant `UPDATE`s), so running the whole set twice is a no-op the second time — there is no migration-tracking table. Any new migration MUST preserve this idempotency or the demo-schema auto-sync goes red on the next merge. Optional `MIGRATE_ONLY_HOST=<substr>` env guard makes it refuse any `DATABASE_URL` whose host doesn't match.
- **`app/api/health` returns the connected DB host** (`{ dbHost, ok }`, host only — never the connection secret), resolved from `DATABASE_URL` — the same single source `lib/db.ts` reads (the `DEMO_DATABASE_URL` precedence was retired in #429). `sync-demo-schema.yml`'s `verify-demo-datasource` job hits `demo.tigerwolves.foulox.me/api/health` after each schema apply (on push to `main`) and fails **red** if the demo isn't reading `demo-data` — the loud catch for the #376 silent mis-point.
- **`scripts/refresh-demo.ts`** — resets the `demo-data` Neon branch from production (on-demand **data** reset only — schema upkeep is now automatic, see above), re-inserts the `run_leaders` row + self-follow for `foulox+demo@gmail.com`, then hits the demo app's revalidate endpoint to flush the Next.js cache. Host-guarded: refuses to run against anything other than `ep-ancient-math-atvtz5p9`. Run it as: `DATABASE_URL=<demo-data-connection-string> NEON_API_KEY=<key> CLERK_SECRET_KEY=<demo-instance-key> npx tsx scripts/refresh-demo.ts`. All three env vars are required; the script errors early if any is missing.
- **Demo code stays current by deploying from `main`.** The `tigerwolves-demo` Vercel project builds from `main` on every push, so no branch-management workflow is needed to keep the demo's **code** current (its **schema** is kept in sync separately by `sync-demo-schema.yml`, #415). The old `ff-staging.yml` that fast-forwarded a `staging` branch — from when the demo rode on the staging deployment — was removed in #429.
- **Neon credentials are already in `.env.local` — use them; do NOT run `neonctl auth`.** `.env.local` holds `NEON_API_KEY` (Neon REST API token) and `DATABASE_URL` (production connection string). For any Preview-branch connection-string fetch, use `NEON_API_KEY` as the bearer token with the REST `connection_uri` pattern in the next bullet — `neonctl`/interactive OAuth is never needed. Agents keep *breaking* the cached `neonctl` OAuth token by reaching for `neonctl auth` when the API key was already here (e.g. #401's build double-refreshed and wrote null tokens into `~/.config/neonctl/credentials.json`, then couldn't apply its own Preview migration). Auto Mode still blocks reading `.env.local` secrets and Neon calls, so a given fetch may still need Lou out of Auto Mode — but the token itself needs no interactive re-auth.
- **`vercel env pull` always returns empty for `DATABASE_URL`** — Vercel's Neon integration resolves `DATABASE_URL` dynamically at deploy time; the value is never stored as a static env var you can pull. Don't try to use `vercel env pull` to get it. Instead, fetch the connection string directly via the Neon REST API: `curl -H "Authorization: Bearer $TOKEN" "https://console.neon.tech/api/v2/projects/{project-id}/connection_uri?branch_id={branch-id}&database_name=neondb&role_name=neondb_owner"`. The token lives at `~/.config/neonctl/credentials.json`. **tigerwolves project ID: `purple-star-02119717`** (corrected 2026-07-26 — this file previously said `spring-salad-36742894`, which doesn't exist on the account and made every `connection_uri` call fail with a useless generic "internal error," costing real time before the ID itself was suspected). Production branch: `br-square-river-atjn0mzq`. test-data branch: `br-tiny-darkness-at3q6q1y` (renamed from `preview/staging`, #429). Durable demo branch: `br-little-rice-at9l08ja`. If the cached token has simply expired (not deauthorized), it can be refreshed non-interactively without `neonctl auth`: POST to `https://oauth2.neon.tech/oauth2/token` with `grant_type=refresh_token`, `client_id=neonctl`, and the `refresh_token` value already in the credentials file — write the response's `access_token`/`refresh_token`/`expires_in` back into that same file (compute `expires_at` as current-time-ms + `expires_in`*1000) so both `neonctl` and direct API calls pick it up.
- **`neonctl auth` races if the browser it auto-opens isn't the one you want to authenticate in.** It opens the OS default browser *and* starts a one-shot local callback server; if you then complete login in a different browser (e.g. the default is Chrome logged into someone else's account, but you want to auth as yourself in Arc), whichever tab hits the callback first wins — even if that hit fails. A stale/mismatched session in the auto-opened browser can crash the callback server with `request_forbidden: No CSRF value available in the session cookie` before your intended browser ever gets there, which then shows a plain "connection refused." Fix: set the browser you intend to use as the OS default *before* running `neonctl auth`, so only one tab ever opens.
- **`.env.local`'s `DATABASE_URL` points at production** — if `.env.local` has a `DATABASE_URL` value at all, it is the production Neon branch. Treat it as production when running migrations.
- **In agent sessions, use the Neon REST API directly instead of `neonctl` or `npx neonctl`** — `neonctl` requires an interactive browser OAuth on first use, and `npx neonctl` still prompts for org selection interactively even with a cached credential. Neither works in a non-TTY agent session. Use the curl pattern above.
- **Always `git fetch origin main` before reading files at the start of a new branch session** — read key files from `git show origin/main:{file}` rather than the local checkout; the local branch may be stale from a previous session on a different machine.
- **There is no tool called `chromium-cli`** — checked npm and Homebrew (2026-07-19), neither has a package by that name; Homebrew's closest match, `chrome-cli`, is a different tool (drives an already-open Chrome window via macOS scripting, not a clean isolated session) and doesn't fit this use case anyway. For browser-driven verification, write a throwaway Playwright script instead — `@playwright/test` is already a devDependency, and Chromium is typically already installed locally (`~/Library/Caches/ms-playwright/`). The onboarding tour no longer auto-launches (#233, 2026-07-21) and `WhatsNewOverlay` stays closed by default in a fresh context (`!storedVersion && !tourSeen` both true), so a fresh `localStorage` no longer needs any suppression setup before navigating.
- **A real Clerk test-leader account exists for signed-in verification** — `.env.local`'s `PLAYWRIGHT_TEST_EMAIL` / `PLAYWRIGHT_TEST_PASSWORD` is a genuine Clerk leader login, not a bypass or mock. Any bug that only reproduces for signed-in leaders should be verified live via Playwright signing in with these credentials — don't settle for static analysis or a screenshot when this account can actually reproduce it (missed on #246, 2026-07-27, where the session didn't know this existed).
- **Upstash Redis (migrated from Vercel KV / `@vercel/kv`)** — package API unchanged (`kv.mget`, `kv.pipeline`, etc.); `KV_REST_API_URL` / `KV_REST_API_TOKEN` env vars are still the right names. Install via Vercel Marketplace → Upstash for Redis, prefix `KV`, Production + Preview environments. Don't use the "Official Redis Cloud" integration — that's a different product with no free tier and incompatible env vars.
- **vitest `@/` path alias** — `vitest.config.ts` has `resolve.alias: { '@': path.resolve(__dirname, '.') }` so route handler tests can use `@/` imports. Already in place; don't remove it.
- **Sentry was scaffolded by hand, not via `@sentry/wizard`** — the wizard CLI needs an interactive TTY/browser login, unavailable in an agent-driven terminal session. If Sentry setup ever needs redoing, expect to hand-write `instrumentation.ts`/`sentry.*.config.ts`/`app/global-error.tsx` again rather than running the wizard.
- **Wiki edits need SSH, not the `GH_TOKEN= ` pattern** — GitHub wikis have no PR mechanism and aren't reachable via `gh`; clone/push directly: `git@github.com:foulox/tigerwolves.wiki.git`, push to `master`. The empty-`GH_TOKEN= ` prefix that unblocks `gh` commands doesn't apply to raw `git push` — that needs `gh`'s own configured SSH auth instead (confirmed working during the #227 PostHog wiki-page restructure, 2026-07-26).
- **If a Neon/DB action is *actually* denied it may be Auto Mode — but VERIFY before assuming (see "evidence before assertion" up top).** Attempt the read-only query first; only if a tool call is *genuinely* blocked (no approval prompt appears) do you ask Lou to switch modes for that one action. Some past sessions did hit a real Auto-Mode block on Neon/DB access (2026-08-03, twice on 2026-08-09; `psql` and a Node script both blocked, and pre-approving in `.claude/settings.local.json` didn't help). **But on 2026-09-18 an agent merely *assumed* it was blocked and deferred all verification for a whole session while Lou was in auto-edit — the block was imagined.** Never preemptively defer verification on the belief that you're blocked: test, and escalate only on a real denial.
- **`vercel env pull` silently returns an empty string for any env var marked "Sensitive" in the Vercel dashboard** — no error, indistinguishable from the var simply not existing for that environment. Hit this with `ANTHROPIC_API_KEY` during #275's backfill work; had to ask Lou to generate a fresh key from the Anthropic Console instead of pulling the existing one. If a pulled var comes back empty, check whether it's marked Sensitive before assuming it isn't set.

## Development
- **A story that adds a schema migration must apply it to at least its own PR's Preview Neon branch before declaring the build done.** Skipping this and just noting "migration not yet run" as a manual step isn't enough — #238 (2026-07-31) shipped a PR that said this, and Lou hit a live `column "id" does not exist` crash testing the Preview URL because nothing had actually run it. Apply the migration to Preview as part of finishing the build; test-data/production migration timing (before or after merge) is still Lou's call, but Preview should never be left broken. **This guardrail has already been silently violated once** — #272 (2026-08-07) declared itself done without the migration actually being applied anywhere real; the gap wasn't caught until #275 stumbled into missing tables mid-build. A self-reported "done" isn't enough — actually query the target database to confirm the new tables/columns exist before considering a schema-migration story finished.
- **A migration reaches FOUR branches over a story's life — Preview is not enough.** Each for a different reason: **Preview** (the PR URL), **test-data** (`br-tiny-darkness-at3q6q1y`), **production** (`br-square-river-atjn0mzq`, at merge), and **demo-data** (`br-little-rice-at9l08ja`, backing `demo.tigerwolves.foulox.me`). The one that bites silently: **CI runs `npm run test:unit` against the test-data branch, not Preview** — so a migration applied only to Preview leaves CI red with `column … does not exist` even though the Preview URL works (hit on #402, 2026-09-18; the fix was applying the same migration to the test-data branch and re-running CI). Apply to the test-data branch as part of the build, not as an afterthought. Production and demo-data are applied at/after merge (production so the live app doesn't error; demo-data so the demo shows the feature — a plain migration apply is enough, no full `refresh-demo.ts` needed).
- **Never commit directly to `main`.** All code changes go through a PR — see [Contributing](https://github.com/foulox/tigerwolves/wiki/Contributing) for the full workflow. **CLAUDE.md updates are the only exception.**
- **Does this change anything the wiki documents** (architecture, data flow, key files, dev workflow, club context)? Update the wiki in the same PR/session — don't defer doc updates, they go stale fast (found during the #85 `/review` pass, 2026-07-03; confirmed again 2026-07-19 when `Contributing.md` had already drifted from CLAUDE.md's Development Workflow section).
- **Active learning: quiz before summarizing.** After any meaningful change — a PR, a bug fix, a new architectural piece — ask Lou 2-4 short questions about what changed and why *before* giving a summary, so Lou reconstructs the understanding via active recall instead of passively reading a wrap-up. Applies especially to Next.js, Clerk, Neon, and the Redis/KV votes store, since Lou wants to be able to lead future developers on this stack, not just approve their output. Kept here rather than in the wiki or Claude's private memory specifically so it survives machine/session switches — an equivalent preference had previously been saved under the wrong project's memory scope and was silently never applied (found 2026-07-19).

## GitHub Workflow

**Issues**
- The issue body is what to build. When the brainstorming or writing-plans phase resolves open questions, edit the body — don't leave resolutions only in comments. Fold context-dependent mid-discussion decisions into the relevant issue rather than filing a new one.
- Write mid-project progress and learnings as a comment on the relevant issue, not in a memory file. Comments are versioned, searchable, and live next to the work.
- Add every issue to a project board at creation — no floating issues. Use `--add-project` on `gh issue create`, or follow up immediately with `gh issue edit N --add-project`.
- Bugs are children of stories, not epics (Epic → Story → Bug). File as separate issues with `Part of #N` — bugs don't require `ready-to-build`; verbal approval plus a posted implementation plan is enough.

**Epics**
- Linking a story to an epic requires two steps — body bullets alone don't create the actual GitHub link:
  1. `gh api repos/{owner}/{repo}/issues/{epic-number}/sub_issues -F sub_issue_id={story-rest-id}` — use the REST numeric ID from `gh api repos/{owner}/{repo}/issues/{number} -q .id` (not the GraphQL node id)
  2. Add the story to the project board
- When filing or updating a story, verify the "Epic: #N" line in the body matches the actual sub_issues parent — they drift silently. Query via GraphQL before adding a new parent (REST 422s with "may only have one parent" if a link already exists).

**PRs**
- Every PR with verification steps gets two labeled sections: **Test plan (Claude)** and **Manual steps (Lou)**.
  - Check off Claude's items (tsc, unit tests, e2e, greps) immediately via `gh pr edit --body-file` — don't wait.
  - When Lou confirms a manual step in chat, update the checkbox on GitHub — verbal "done" is not sufficient.
  - PR also carries the full AC list from the story so Lou tests against the PR, not the issue.
- An account-wide default PR template lives at `foulox/.github/.github/PULL_REQUEST_TEMPLATE.md` — applies to any foulox repo without its own. Check there before saying "no template applies": `gh api repos/foulox/.github/git/trees/main?recursive=true --jq '.tree[].path'`.
- Rulesets and branch protection require GitHub Pro on private repos — both APIs return 403 on a free personal account. "Require PR before merging" is also whole-branch only, not path-scoped.
